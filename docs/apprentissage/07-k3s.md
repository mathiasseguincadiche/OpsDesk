# 07 — Kubernetes avec K3s : une copie d'essai d'OpsDesk

> Énoncé de référence, lisible sans Notion. Le cours complet (explications, exemple travaillé, indices) est dans la fiche Notion de l'exercice 07, accessible sur invitation. Schéma : [Ingress, Service, pods et Deployment](../diagrams/pedagogique-k3s.svg).

**Objectif.** Faire tourner une copie d'essai d'OpsDesk dans K3s sur `srv-k3s`, et savoir lire ce que Kubernetes fait des déclarations : quels pods tournent, lesquels reçoivent du trafic, et pourquoi.

**Durée estimée** : 5 à 7 heures. **Prérequis** : `srv-k3s` créée et configurée (exercices 04 et 05), exercice 06. **État** : prévu, non vérifié.

## Pourquoi

OpsDesk n'a pas besoin de Kubernetes : Docker Compose suffit pour le service réel. K3s est là pour pratiquer l'orchestration sans risque, sur une copie avec sa propre base de test ([Docker Compose et K3s](../architecture.md#docker-compose-et-k3s)). K3s garde son propre moteur, containerd : Docker n'est pas installé sur `srv-k3s`.

## L'essentiel à comprendre

- On ne lance pas de conteneur : on **déclare un état voulu**, et le cluster le maintient.
- Un Deployment garde N pods en vie ; un Service leur donne un nom stable et ne vise que les pods **prêts** ; un Ingress (Traefik dans K3s) fait entrer le trafic HTTP.
- `readinessProbe` sur `/health/ready` retire un pod du trafic sans le redémarrer ; `livenessProbe` sur `/health/live` le redémarre s'il ne répond plus. Inverser les deux fait redémarrer l'API en boucle quand la base tombe.
- Un seul nœud : aucune haute disponibilité ; si `srv-k3s` tombe, tout tombe.
- Tant que la CI ne publie rien (exercice 08), les images s'exportent avec `docker save` sur `srv-app`, puis se chargent dans K3s par `k3s ctr images import` : c'est le même format OCI.
- Le réflexe de diagnostic : `kubectl get`, puis `describe`, puis `logs`.

## Ce qu'il faut obtenir

Dans un namespace `opsdesk-essai` : un Secret ; PostgreSQL 17 (Deployment, PVC, Service) ; l'API (Deployment avec les deux sondes, Service) ; l'interface (Deployment, Service, `BACKEND_URL` vers le Service de l'API) ; un Ingress pour un nom choisi, par exemple `opsdesk.k3s.lab`. Les YAML vont dans le dépôt, jamais les valeurs du Secret.

Puis quatre expériences, sorties à l'appui : supprimer le pod de l'API ; arrêter la base ; supprimer le pod de la base et relire un ticket ; passer l'API à deux pods.

## Vérifications

| Ce que tu vérifies | Commande | Résultat attendu |
| --- | --- | --- |
| Tout est prêt | `kubectl -n opsdesk-essai get pods` | Trois pods `1/1 Running` |
| Services alimentés | `kubectl -n opsdesk-essai get endpoints` | Au moins une adresse par Service |
| Accès par l'Ingress | `curl -i http://opsdesk.k3s.lab/health/ready` depuis l'hôte | `200`, `"database":"up"` |
| Parcours complet | `python3 scripts/smoke.py http://opsdesk.k3s.lab` | `ALL GOOD` |
| Persistance | Expérience 3 | Ticket relu à l'identique |

## Pièges fréquents

`ImagePullBackOff` (image non importée) ; `CrashLoopBackOff` (lire `kubectl logs --previous`) ; `Running` mais `0/1` (sonde de disponibilité en échec) ; Service sans endpoints (sélecteur et étiquettes différents) ; `404` de Traefik (nom d'hôte de l'Ingress).
